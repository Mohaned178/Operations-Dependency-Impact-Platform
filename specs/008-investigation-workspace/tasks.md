## Rules for the implementer (read first)

1. **Order**: do tasks **in ID order** within a phase. `[P]` tasks touch different files and may be done in any order. Do one phase at a time.
2. **Re-read before each task**: the section the task references:
   - research.md (R#);
   - data-model.md (§#);
   - contracts/api.md (§ name, fixture V#);
   - plan.md "Key Design Notes" (KDN #).

   **Do not invent alternatives.** The strings and values in contracts/api.md § Text templates and § Acceptance fixtures are exact. Assert them literally.
3. **Forbidden**:
   - new dependencies (Node built-ins such as `crypto` and `child_process` are not dependencies);
   - `any`, `TODO`s, and non-null `!` (use `.at()` with a check and throw an invariant `Error`);
   - `localeCompare` (API: compare strings only with `compareCodeUnits` from `apps/api/src/graph/traversal/path-order.ts`; web: keep the server's order, never sort strings client-side);
   - `WITH RECURSIVE`, calls to `GraphRepository` or `TracingService`, or any traversal code in `apps/api/src/investigations/`. This feature adds **none**. Graph work happens only through `SnapshotService` and `TimelineService`;
   - `new Date()` or `Date.now()` in `apps/api/src/investigations/rules/`, in `apps/api/src/investigations/investigation.mapper.ts`, in `packages/shared/src/investigations.ts` and in `packages/shared/src/analysis-snapshots.ts` (pure code receives `now` / `evaluatedAt`);
   - inline permission checks in services (always call `rules/policy.ts`, KDN 6);
   - edit or delete endpoints for investigations, pins, decisions or notes;
   - notifications, risk features, workflows, file uploads or AI;
   - accepting an analysis result or an evaluation time from the client for a pin;
   - `DROP TABLE exception_snapshots`, `DROP TYPE "ExceptionSnapshotKind"`, `prisma migrate reset` on a shared database to "fix" the migration, or `prisma db push`.
4. **No changes to earlier features' behavior**:
   - do not change any 003 to 007 response shape, rule, text, audit row or seed row (§39, §40, 007 seed);
   - the only allowed differences in 007 output are the two **additive optional snapshot fields** `chosen.chain` and `digest.impact.slaCommitments` (research R2), nothing else;

**Decisions fixed by this task list** (they close small gaps in the design documents; do not revisit them):
- D1. `trimmed` and `optionalTrimmed` are **imported** from `./exceptions` (007 exports them). The `csv` helper moves to `common.ts` as exported `csvArray` (plan: `common.ts`) and 007's `exceptions.ts` imports it (T003). `investigations.ts` never redefines them.
- D2. 007's `Errors.versionConflict(currentVersion)` gets an optional second parameter: `versionConflict(currentVersion: number, subject: 'exception' | 'investigation' = 'exception')`. The message is `` `The ${subject} was changed by someone else` ``. Default behaviour is unchanged (T014). contracts/api.md needs the `investigation` wording.
- D3. Action names used in `auth.forbidden` metadata and in the closed-state message (`` `${ACTION} is not allowed while the investigation is CLOSED. Reopen it first.` ``): `EDIT`, `CHANGE_OWNER`, `PIN`, `UNPIN`, `ADD_ENTITY`, `REMOVE_ENTITY`, `LINK_EXCEPTION`, `UNLINK_EXCEPTION`, `DECIDE`; transitions use `RESOLVE`, `CLOSE`, `REOPEN` (the pair message of research R4 applies, because a CLOSED row has `REOPEN` only).
- D4. `PATCH` with `ownerId`: the caller must be the owner or a manager, else 403 with action `CHANGE_OWNER` (checked before the version). An `ownerId` equal to the current owner is dropped from the change set. Any other edited field needs `canEdit` (action `EDIT`). A PATCH on a CLOSED investigation is 409 with ACTION `EDIT` whatever the fields.
- D5. The `unpin` permission flag equals `canPin`. Unpin order: 404 (investigation, then a pin that is not of this investigation) → 403 (`UNPIN`) → version → CLOSED (`UNPIN`) → already unpinned is a 200 no-op.
- D6. Timeline cursor filter key: `TimelineService.listForEntities` takes `filterKey: string | null`. When non-null, the cursor is `encodeCursor({ at, kindRank, id, f: filterKey })` and a cursor whose `f` differs gives 400 `cursor` `Invalid cursor`. `list()` passes `null`, so the per-entity cursor and output stay byte-identical. `filterKey` = first 16 hex characters of the SHA-256 (Node `crypto`) of the canonical JSON of the filters (keys sorted, arrays sorted and de-duplicated, absent values omitted), computed by the investigations code.
- D7. `ExceptionsQueryService.summariesByIds(ids: string[], actor: Actor, evaluatedAt: Date): Promise<ExceptionSummaryDto[]>` is added (T014) and used for `linkedExceptions`. It returns the DTOs in the order the caller sorts them; it never runs an analysis.
- D8. `chooseCandidate` (007 T019) is not a shared function. When `snapshot.mapper.ts` is removed it moves unchanged to `apps/api/src/exceptions/choose-candidate.ts` with its spec (T004).
- D9. The GIN index is declared in `schema.prisma` as `@@index([chainEntityIds], type: Gin)`, so Prisma knows it. Its name is `analysis_snapshots_chain_entity_ids_idx` and the migration uses that name, not `…_gin` of data-model §1b.
- D10. The two additive snapshot fields change stored 007 payloads, 007 response bodies and 007 audit digests. They are allowed (rule 4). The golden file of T002 is compared **after stripping** `chosen.chain` and `digest.impact.slaCommitments` (T011).
- D11. `DecisionDto.laterStatus` follows the contract (array of `{ citationIndex, status }`), not the prose of research R10.
- D12. `InvestigationsService.create(actor, body, info, opts?)` takes `opts?: { rootCauseEvaluatedAt?: string; createdFrom?: 'SEED' }` for the seed only (as 007 D9). The HTTP schema never accepts `SEED`. The seed's system actor stores `createdById`, `takenById`, `linkedById` and `addedById` as `null` and writes `actorType: 'system'`.
- D13. 007's `OwnerPicker` gets one optional prop `kinds?: Array<'USER' | 'TEAM'>` (default both) so investigations can pick users only (research R16). Defaults reproduce today's behaviour; its tests stay unchanged (T028).
- D14. The Entity 360 Investigations section cannot show scope reasons (the list DTO carries none). It shows `Focus` when `item.focus.id` equals the entity id and `In scope` otherwise; the full reasons are on the investigation's Related Entities tab. (This differs from quickstart §3 step 9 and spec Story 6 scenario 5; see the final report of this task list.)
- D15. `InvestigationCore` (the audited shape) has exactly the keys `title`, `description`, `severity`, `owner` (`{ id, name }`), `status`, `resolutionSummary`, `resolvedAt`, `resolvedBy` (`{ id, name } | null`), `closedAt`, `closedBy`, `reopenCount`, in `INVESTIGATION_FIELD_ORDER` order. `rootCause` and `impact` appear in audit rows and history only as digests inside `investigation.created`, `pinned` and `unpinned` rows.
- D16. Shared guard code for mutating services lives in `apps/api/src/investigations/investigation-guard.service.ts` (T018): `loadRow`, `refuse`, `assertVersion`, `assertNotClosed`, `conditionalUpdate`, `touch`, `actorName`. Every service uses it; nothing is copied.
- D17. The impact-anchor rule is one pure function, `resolveImpactAnchor` in `rules/impact-anchor.ts` (T017), used by create and by pins.
